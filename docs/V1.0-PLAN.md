# Unified Chat — V1.0 Product Plan

> Product direction is fixed: Local-first unified chat, hidden browser implementation, isolated Profiles, unified inbox, global search, translation router, translation memory, and lightweight AI.

## 1. Product definition

**Unified Chat** is a desktop chat workspace, not a browser manager, CRM, dashboard, campaign tool, or automation suite.

Core principles:

- No account required for the local application.
- Local first.
- Multiple isolated Profiles.
- WhatsApp + Telegram as the first providers.
- DeepL first, Google as automatic fallback.
- AI only when needed, exposed through `✨`.
- One unified inbox.
- One global search.
- One translation memory.
- One clean interface.

## 2. Four-layer architecture

```text
                    Unified Chat
                         │
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
   Profile Layer    Message Layer    Intelligence Layer
        │                │                │
   多账号隔离        统一聊天          翻译 / AI
        │                │                │
        └────────────────┼────────────────┘
                         ↓
                  Local Data Layer
```

### Profile Layer

A Profile is a digital workspace. The user sees `WhatsApp · Personal`, `WhatsApp · Work`, `Telegram · Personal`, etc. The browser implementation remains invisible.

Each Profile owns independent:

- Session
- Cookie
- Local Storage
- IndexedDB
- Cache
- Window state
- Network settings
- Translation settings
- AI settings

Profile switching is available from the top bar and through `Ctrl+1`, `Ctrl+2`, `Ctrl+3` where profiles exist.

### Message Layer

Normalise provider messages into one internal conversation/message model. The UI should not need provider-specific layouts.

V1 includes:

- Unified Inbox
- All / Unread / Mentions / Favorites / Follow Up
- Cross-profile conversation identity
- Last-conversation restoration
- Global search across profiles and providers

### Intelligence Layer

Translation and AI remain separate from provider adapters.

Translation pipeline:

```text
Message
  ↓
Conversation/Profile settings
  ↓
Translation Router
  ├── DeepL
  └── Google fallback
  ↓
Local translation cache
  ↓
UI
```

V1 translation behaviour:

- DeepL is the preferred provider.
- Google is automatic fallback.
- Cache identical translation requests locally.
- Batch consecutive short messages before translation.
- Apply Global → Profile → Conversation settings in that order, with the most specific setting winning.
- Support natural/casual/professional tone and natural/short/detailed length.
- Support per-Profile personal dictionaries / translation memory.

AI remains hidden behind `✨` with:

- Reply
- Rewrite
- Explain
- Summarize
- Translate

No persistent AI assistant panel.

### Local Data Layer

Own local persistence, profile metadata, conversation index, translation cache, dictionaries, UI state, and backup metadata.

Credentials and browser storage are not included in normal Profile Backup exports.

## 3. Security and recovery

### Profile Vault

Startup and lock state are represented by a local Profile Vault.

Supported concepts:

- Windows Hello
- Local password
- Trusted Device for automatic unlock
- `Ctrl + Shift + L` Quick Lock

Quick Lock must hide both the main chat UI and isolated provider workspaces. Unlock restores the previous workspace state.

### Profile Backup

Backup exports configuration rather than credentials by default.

Included:

- Profile settings
- Translation settings
- UI settings
- Local configuration
- Profile-scoped dictionary / translation memory configuration

Optional encrypted backup can be supported without changing the normal backup contract.

## 4. Conversation Profile precedence

```text
Global Settings
       ↓
Profile Settings
       ↓
Conversation Settings
```

The most specific value wins.

Conversation-level controls include:

- Source / target language
- Translation provider
- Translation style
- Bilingual / translated display
- AI tone

## 5. UI contract

Primary navigation is intentionally small:

```text
Chats
Profiles
Search
Settings
```

The home screen opens directly into Chats.

Top bar:

```text
☰   Unified Chat   Search everywhere...        🟢 Personal ▼   🔔   🔒
```

The active Profile switcher is the main account/workspace entry point. Browser terminology must not appear in normal user-facing UI.

## 7. Provider abstraction

Providers implement an adapter contract rather than leaking provider-specific logic into the UI.

```text
ProviderAdapter
├── provider id
├── connect / restore
├── health
├── list conversations
├── sync messages
├── open conversation
└── send message
```

Initial adapters:

```text
WhatsAppAdapter
TelegramAdapter
```

Future providers must plug into the same contract without changing the four-layer architecture.

## 8. V1 acceptance criteria

- User can create and switch Profiles without seeing browser terminology.
- Each Profile keeps its own isolated provider session/workspace.
- Opening a Profile restores the provider and last conversation.
- Unified Inbox shows conversations from multiple Profiles/providers.
- Global search returns results across Profiles/providers.
- Translation uses DeepL first and Google fallback through one router.
- Translation cache prevents repeated identical requests.
- Consecutive short messages can be batched before translation.
- Profile and Conversation translation settings override broader defaults correctly.
- Profile backup excludes sensitive login credentials by default.
- Quick Lock hides chat content and provider workspaces.
- `✨` exposes AI actions without adding an AI dashboard.
- The default landing view is Chats.

## 9. Deliberate non-goals for V1

Do not add:

- CRM
- Campaigns
- Contact-management dashboard
- Statistics dashboard
- Automation builder
- Browser-management UI
- Fingerprint terminology
- Persistent AI assistant sidebar

These would move the product away from the fixed `Unified Chat` direction.

## 10. Implementation direction

The current desktop foundation is Electron + Vite + React/TypeScript. Keep that direction for V1 rather than introducing a second desktop runtime prematurely.

Chromium/BrowserView/session isolation remains an implementation detail behind Profile Layer APIs. The renderer should consume Profile and Message abstractions only.

The next engineering priority after the current Conversation Profile work is to make the global-search result flow first-class: indexed search → result selection → activate Profile → restore/open conversation.
